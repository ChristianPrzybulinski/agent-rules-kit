# KIT-072 — Each consumer project pins the kit version it uses

## Problem and evidence

[FACT] Stratics vendors 23 skills (`.claude/skills/*/.agent-rules-kit` = "kit 12.1.0 generated by
platforms/tools/sync-project.sh") and also enables `guardrails@ai-kit` in its `.claude/settings.json` and in the owner's
`~/.claude/settings.json`. On 2026-11-15 `~/.claude/plugins/installed_plugins.json` held 26 `guardrails@ai-kit` records
(25 project scope: `stratics-docs` and loop worktrees; 1 user scope) with four different `gitCommitSha` values
(`35a2203`, `fc38984`, `3807c85`, `6ba19cb`), and every record's `installPath` was the same directory,
`~/.claude/plugins/cache/ai-kit/guardrails/12.1.0`. Claude Code names the cache directory after the plugin's version, the
manifest `version` comes first, and the kit keeps `12.1.0` between releases, so `refresh.sh` (KIT-013) rewrites that one
directory after each kit merge and every Stratics session loads the kit head's skills, hooks and agents.

[FACT] The same sessions list each vendored skill twice, `/name` and `/guardrails:name` (KIT-071 listing baseline).
A read-only run of this change's doctor check on the owner's state reports 15 checkouts that vendor kit copies and load
`guardrails@ai-kit` beside them (`stratics-docs` and 14 loop worktrees).

## Verified constraints

Checked against Claude Code 2.1.287 (`claude --version`), its official docs (code.claude.com/docs, fetched 2026-11-15:
`plugins/marketplace-reference`, `plugins/loading`, `settings`, `settings-reference`, `skills`, `commands`) and probes in
an isolated `CLAUDE_CONFIG_DIR` that left the owner's settings untouched; Codex from codex-cli 0.164.0 and the owner's
`~/.codex/config.toml`.

- A marketplace source takes `ref` = branch or tag; a commit SHA needs Claude Code 2.1.324 or later. A user registers
  one marketplace per name, `known_marketplaces.json` is one per user, and a same-name entry from a higher settings file
  replaces the lower one whole. A plugin's cache directory is `cache/<marketplace>/<plugin>/<version>/`. So two
  projects cannot hold two refs of `ai-kit`, and a per-version marketplace needs an inline `settings` source whose
  external plugin source Claude Code fetches only when user, untracked local, flag or managed settings enable it, never
  project settings: each clone and loop worktree would need a manual install.
- `enabledPlugins` merges key by key, project over user, local over project: a project `"guardrails@ai-kit": false`
  turns the user plugin off for the repository (probe: `enabled: false`).
- A plugin folder under the project's `.claude/skills/` with `.claude-plugin/plugin.json` loads in place as
  `<name>@skills-dir`, scope `project`, with its skills, agents and four hooks (probe, `claude plugin details`), after
  the workspace trust check. An installed `guardrails@ai-kit` keeps the name `guardrails` even while disabled: the copy
  reported `Not loaded — the name "guardrails" is already taken by an installed plugin`. Renamed `guardrails-pinned`, it
  loaded.
- A project skill replaces a bundled command but not its aliases, and `/review` is an alias of the bundled
  `/code-review` (docs `skills` § Resolve skills that share a name, `commands`). So the always-on skill `review` cannot be
  vendored as a plain skill; inside the pinned plugin it stays `guardrails-pinned:review`.
- Project settings and repository plugins are read from the session's starting folder only (probe from a subfolder:
  `guardrails@ai-kit` enabled), and the desktop app loads a worktree's repository plugin from the main checkout.
- Codex loads the always-on file through `~/.codex/AGENTS.md` → `~/.ai-kit/plugins/guardrails/AGENTS.md` and the
  plugin from marketplace `ai-kit` with `ref = "main"`; `refresh.sh` runs `codex plugin marketplace upgrade ai-kit` and
  pulls `~/.ai-kit`. Claude Code's `~/.claude/CLAUDE.md` links the same file. None of these is per project.

## Options weighed

- (a) Pin the marketplace ref per project: rejected by the first constraint (one marketplace per name, one cache per
  version, no SHA ref on 2.1.287; per-version marketplaces need a manual install in every worktree).
- (b) Turn the plugin off at project scope and vendor the hooks: chosen, with the hooks, agents and the skills not
  vendored plain carried by a skills-directory plugin instead of `settings.json` hooks, because plain copies cannot
  carry `review` (bundled alias) or the agents' plugin-qualified preloads.
- (c) Record the version and warn on drift: kept as part of (b) (`KIT_COMMIT`, `--check`, `doctor.sh`); alone it would
  leave every kit merge reaching the project.

What would prove (b) wrong: a Claude Code release that stops loading repository plugins from `.claude/skills/`, or a
session at a trusted repository root where `/plugin` shows `guardrails@ai-kit` enabled after the resync.

## Change

- `platforms/tools/sync_pinned_plugin.py` (new): writes `.claude/skills/guardrails-pinned/` from `plugins/guardrails/`
  (`.claude-plugin/plugin.json` renamed `guardrails-pinned`, `hooks/`, `templates/`, `agents/` with each
  `guardrails:<skill>` preload renamed to `guardrails-pinned:<skill>` or to the plain copy's name, and every skill the
  profile does not copy as a plain skill), marks it, prints `KIT_COMMIT`, its hashes and `copies` (the hash of every
  `.github/spec-lint/` file `kit_files()` lists, through `pin_sources`) for the manifest, refuses an
  unmarked folder, removes a marked copy in plugins mode, and checks the copy, `settings.local.json` and `claude plugin
  list`.
- `platforms/tools/sync-project.sh`: the pin lives in one block of `pin_*` functions (coordinator request, so the parallel
  KIT-070, KIT-073 and KIT-074 merges stay mechanical); vendored mode writes the copy, records the pin in `KIT_MANIFEST.json`, sets
  `guardrails@ai-kit` to `false` and `guardrails-pinned@skills-dir` to `true`; `--check` expects them and calls the pin
  check; plugins mode is unchanged.
- `platforms/tools/doctor.sh`: warns about each project with an `@ai-kit` install record that vendors kit copies but
  still loads `guardrails@ai-kit`, and counts the pinned ones. `refresh.sh` is unchanged: it updates, installs and
  reinstalls user-scope plugins only, and the pin is a repository file it never writes.
- `README.md`, `docs/projects.md` (the pin, what stays unpinned, the migration), `platforms/tools/README.md`.

## Proof

`bash platforms/tools/check.sh`, `CI=1 bash platforms/tools/check.sh`, `bash platforms/tools/smoke.sh` (vendored sync
writes the copy and turns the head off; doctor reports a leaking and a pinned project),
`python3 platforms/ci/validations/check_kit.py --links`, `test_sync_project.py` (10 new tests: copy contents and
settings for three profiles, agent preloads, drift in the copy, the head re-enabled in project or local settings, the
`claude plugin list` probe with a stub, collision refusal, migration of a pre-pin vendored repository, plugins mode
unchanged, and a kit copy whose `kit_files()` lists a fake schema: the pin records it, a changed or deleted copy fails
`--check`, and a pin from before the entry reports it missing from the pin), and an end-to-end run on Claude Code 2.1.287 in an isolated config: after the sync of a
`docs,godot:client,java:server,python:platform` repository `claude plugin list` shows `guardrails@ai-kit` disabled and
`guardrails-pinned@skills-dir` 12.1.0 enabled with 5 skills, the repository holds 22 plain copies, no kit skill is listed
twice, and `sync-project.sh --check` with the live CLI passes.
