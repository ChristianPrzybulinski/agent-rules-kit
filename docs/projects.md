# What lives in a project that uses the kit

Rules, skills, references and templates are authored **in the kit** under `plugins/` and reach the agent through the plugin marketplaces or `bootstrap.sh`. The project receives its own artifacts plus generated, version-stamped copies (table below). Real example: the `stratics-docs` repository.

## In the project

| Artifact | Origin in the kit | Example (stratics-docs) |
|---|---|---|
| repo `AGENTS.md` | `plugins/guardrails/templates/project-agents-*.md` filled in | `AGENTS.md` (scope, commands, boundaries) |
| `docs/spec/` | created by `platforms/kits/sdd/init-spec.sh`; artifacts follow `plugins/guardrails/templates/spec-*` and `platforms/ci/schemas/` schemas | `docs/spec/spec.md`, `features/FEAT-0nn.md`, `requirements/`, `decisions/`, `debts/` |
| `docs/sessions/` | `plugins/guardrails/templates/doc-session-handoff.md` | `docs/sessions/2026-09-30-initial-specs.md` |
| `docs/legacy/` (or reports) | `plugins/*/templates/doc-*.md` | `docs/legacy/evidence.md` etc. |
| `.github/spec-lint/` | copy generated by `platforms/tools/sync-project.sh` (`check_spec.py` + schemas + `KIT_VERSION`) | local spec validation in the project's CI |
| `.claude/rules/<plugin>-<rule>.md` | generated by `platforms/tools/sync-project.sh` from `plugins/<plugin>/rules/` for the repo profile, marker line names the source and kit version; a `<profile>:<dir>` entry prefixes with `<dir>/` the globs of the rule named after the profile (`godot:client` scopes `dev-godot.md`, never `dev-java.md`) | path-scoped rules for Claude Code in cloud sessions, CI and new machines |
| `CLAUDE.md` | generated by `platforms/tools/sync-project.sh`: a marker comment plus `@AGENTS.md` (`AGENTS.md` stays the single source) | same content on Claude Code before 2.1.277, in the GitHub Action and in cloud sessions |
| `.claude/settings.json` | generated by `platforms/tools/sync-project.sh`: `extraKnownMarketplaces.ai-kit` and `enabledPlugins` for the repo profile (`godot`, `java`, `docs`, `python`, or a monorepo's comma list such as `docs,godot:client,java:server`, which enables the union); other keys preserved | each collaborator's local Claude Code loads only the plugins the repo uses |
| `.claude/skills/<name>/` + `KIT_MANIFEST.json` | copy of `plugins/<plugin>/skills/<name>/` for the repo profile, generated by `platforms/tools/sync-project.sh --vendor-skills`, marker `.agent-rules-kit`, sha256 per file in the manifest; the manifest also records the profile list, which a sync without `--profile` reuses | skills in Claude Code cloud sessions, the GitHub Action, Devin Cloud and new machines |
| `.github/workflows/` | `platforms/kits/github/workflows/` | `docs-checks.yml` (runs the local copy — no kit checkout/token; any filename works, `sync-project.sh` detects it by content), `gitleaks.yml`, `reusable-ci-*.yml` |
| `.github/PULL_REQUEST_TEMPLATE.md`, `CODEOWNERS`, `dependabot.yml`, labels, root `REVIEW.md` | `platforms/kits/github/` | ditto + `scripts/labels-sync.sh`; `REVIEW.md` is copied to the repository root, not to `.github/` |
| `infra/` / compose | `platforms/kits/docker/` | `infra/compose.yml` (`name: stratics`) |
| `.gitattributes` (LFS) | `platforms/kits/git-lfs/` | the repo's first commit |

IDs in `docs/spec/`: `FEAT-nnn`, `REQ-F-nnn`, `REQ-NF-nnn`, `DTEC-nnn`/`DGME-nnn`/`DPRO-nnn`, `DEBT-nnn` — sequential numbering, `id` = the file name's prefix, status in frontmatter (`proposed`/`approved`/`delivered`…). Process: `plugins/guardrails/skills/sdd-constitution/references/sdd-process.md`.

## What does NOT go to the project

- Skills stay in the kit and reach the machine through the plugin install; a project may vendor the skills of its profile into `.claude/skills/` with `platforms/tools/sync-project.sh --vendor-skills` (never by hand), like the generated `.claude/rules/` copies in the table above. Knowledge is not copied.
- Spec schemas and validators reach the project as a **deliberate copy** in `.github/spec-lint/` (no link to the kit in CI — the kit repo may not even exist at CI time). Update: `sync-project.sh <repo>`; divergence detectable with `sync-project.sh --check`. The same sync maintains `CLAUDE.md` and `.claude/settings.json`. Reusable workflows **between repos of the same product** (e.g.: `stratics-client` → `stratics-docs/.github/workflows/reusable-ci-*.yml`) are allowed — what is avoided is depending on the kit.
- Legacy archive originals: only reports/manifests enter the repo (project rule, see stratics-docs' `docs/legacy/README.md`).
