# What lives in a project that uses the kit

Rules, skills, references and templates are authored **in the kit** under `plugins/` and reach the agent through the plugin marketplaces or `bootstrap.sh`. The project receives its own artifacts plus generated, version-stamped copies (table below).

## In the project

| Artifact | Origin in the kit | Example (a docs repository) |
|---|---|---|
| repo `AGENTS.md` | `plugins/guardrails/templates/project-agents-*.md` filled in | `AGENTS.md` (scope, commands, boundaries) |
| `docs/spec/` | created by `platforms/kits/sdd/init-spec.sh`; artifacts follow `plugins/guardrails/templates/spec-*` and `platforms/ci/schemas/` schemas; `spec.md` carries the project's `sdd:` process parameters (`plugins/guardrails/skills/sdd-constitution/references/sdd-parameters.md`, KIT-067) | `docs/spec/spec.md`, `needs/NEED-0nn-slug.md`, `features/FEAT-0nn.md`, `requirements/`, `decisions/`, `debts/` |
| `docs/sessions/` | `plugins/guardrails/templates/doc-session-handoff.md` | `docs/sessions/2026-09-30-initial-specs.md` |
| `docs/legacy/` (or reports) | `plugins/*/templates/doc-*.md` | `docs/legacy/evidence.md` etc. |
| `.github/spec-lint/` | copy generated by `platforms/tools/sync-project.sh` (`check_spec.py` + schemas + `KIT_VERSION`) | local spec validation in the project's CI |
| `.claude/rules/<plugin>-<rule>.md` | generated by `platforms/tools/sync-project.sh` from `plugins/<plugin>/rules/` for the repo profile, marker line names the source and kit version; a `<profile>:<dir>` entry prefixes with `<dir>/` the globs of the rule named after the profile (`godot:client` scopes `dev-godot.md`, never `dev-java.md`) | path-scoped rules for Claude Code in cloud sessions, CI and new machines |
| path-rule block in a folder's `AGENTS.md` | generated by `platforms/tools/sync-project.sh` from the same rendered rules, one block per folder a rule's globs start in, between `agent-rules-kit: path rules` markers; `spec.md` `sdd.rule_paths` moves a rule to other folders (KIT-067) | the rules for Codex and other runtimes that load no rule by path; the root block also reaches Claude Code through `CLAUDE.md` |
| `CLAUDE.md` | generated by `platforms/tools/sync-project.sh`: a marker comment plus `@AGENTS.md` (`AGENTS.md` stays the single source) | same content on Claude Code before 2.1.277, in the GitHub Action and in cloud sessions |
| `.claude/settings.json` | generated by `platforms/tools/sync-project.sh`: `extraKnownMarketplaces.ai-kit`, `includeGitInstructions: false` (KIT-071) and `enabledPlugins`: `guardrails@ai-kit: true` in plugins mode; in vendored mode `guardrails@ai-kit: false` and `guardrails-pinned@skills-dir: true` (KIT-072); other keys preserved | each collaborator's local Claude Code loads the kit once, from the plugin install or from the pinned copy |
| `.claude/skills/<name>/` + `KIT_MANIFEST.json` | copy of `plugins/<plugin>/skills/<name>/` for the repo profile, generated by `platforms/tools/sync-project.sh --vendor-skills`, marker `.agent-rules-kit`, sha256 per file in the manifest; the manifest also records the profile list, which a sync without `--profile` reuses, and the pin: `KIT_VERSION`, `KIT_COMMIT`, the pinned copy's hashes and `copies`, the hash of each `.github/spec-lint/` file (KIT-072) | skills in Claude Code cloud sessions, the GitHub Action, Devin Cloud and new machines |
| `.claude/skills/guardrails-pinned/` | vendored mode only (KIT-072): the rest of `plugins/guardrails/` at the synced version (hooks, agents, templates and every skill not copied as a plain `.claude/skills/<name>/`), written by `platforms/tools/sync_pinned_plugin.py`, marker `.agent-rules-kit`; agent preloads name `guardrails-pinned:<skill>` or the plain copy | the guard hooks, the subagent profiles and the always-on skills at the project's kit version, loaded by Claude Code as `guardrails-pinned@skills-dir` once the folder is trusted |
| `.github/workflows/` | `platforms/kits/github/workflows/` | `docs-checks.yml` (runs the local copy — no kit checkout/token; any filename works, `sync-project.sh` detects it by content), `gitleaks.yml`, `reusable-ci-*.yml` |
| `.github/PULL_REQUEST_TEMPLATE.md`, `CODEOWNERS`, `dependabot.yml`, labels, root `REVIEW.md` | `platforms/kits/github/` | ditto + `scripts/labels-sync.sh`; `REVIEW.md` is copied to the repository root, not to `.github/`, by `sdd-constitution` § 5, which removes the lines a project gate enforces |
| `infra/` / compose | `platforms/kits/docker/` | `infra/compose.yml` (`name: <project>`) |
| `.gitattributes` (LFS) | `platforms/kits/git-lfs/` | the repo's first commit |

IDs in `docs/spec/`: `NEED-nnn`, `FEAT-nnn`, `REQ-F-nnn`, `REQ-NF-nnn`, `DEC-nnn` (or one prefix per decision kind that `spec.md` `decision_kinds` declares), `DEBT-nnn` — sequential numbering, `id` = the file name's prefix, status in frontmatter (`proposed`/`approved`/`delivered`…). Process: `plugins/guardrails/skills/sdd-constitution/references/sdd-process.md`.

## What does NOT go to the project

- Skills stay in the kit and reach the machine through the plugin install; a project may vendor the skills of its profile into `.claude/skills/` with `platforms/tools/sync-project.sh --vendor-skills` (never by hand), like the generated `.claude/rules/` copies in the table above. Knowledge is not copied.

## Pinning the kit version (KIT-072)

A vendored project uses the kit version it last synced, in every local Claude Code session started at its root. The plugin install cannot pin per project: Claude Code keeps one `ai-kit` marketplace clone per user and one plugin cache directory per version (`~/.claude/plugins/cache/ai-kit/guardrails/<version>/`), and the kit's manifest version stays the same between releases, so `refresh.sh` rewrites that directory after each kit merge. The vendored sync therefore copies the rest of the plugin into `.claude/skills/guardrails-pinned/` and turns `guardrails@ai-kit` off for the project; a kit merge changes nothing there until the next `sync-project.sh` run, and the resync PR is the version bump. `sync-project.sh --check` reports a pinned copy or `.github/spec-lint/` file that differs from `KIT_MANIFEST.json`, a `kit_files()` entry the pin lacks, a `settings.local.json` that re-enables `guardrails@ai-kit` and, when the `claude` CLI is on `PATH` outside CI, what Claude Code lists for the repository; `doctor.sh` warns about each project that vendors kit copies but still loads `guardrails@ai-kit`.

Not pinned, still the user install: `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md` (the always-on `AGENTS.md` from the `~/.ai-kit` clone), the Codex plugin (marketplace `ref = "main"`), Devin's plugin, a session started in a subfolder (Claude Code reads the project's `.claude/settings.json` and repository plugins from the session's starting folder only), and a desktop-app worktree, which loads the repository plugin from the main checkout.

Migration for a vendored project from before KIT-072:

1. Run `platforms/tools/sync-project.sh <repo>` from the kit version to pin (the manifest keeps the vendored mode and profile). It writes `.claude/skills/guardrails-pinned/`, sets `guardrails@ai-kit` to `false` and `guardrails-pinned@skills-dir` to `true`, and records `KIT_COMMIT`.
2. Commit the result in one PR; `sync-project.sh --check <repo>` passes on it.
3. Remove anything that writes `guardrails@ai-kit: true` back into the project's `.claude/settings.json`, such as `claude plugin install guardrails@ai-kit --scope project` in a worktree script; a `.claude/settings.local.json` that enables it loads the kit head beside the pin.
4. Open a session at the repository root and run `/plugin` (or `claude plugin list` there): `guardrails-pinned@skills-dir` is enabled, `guardrails@ai-kit` disabled, and each kit skill appears once.
5. To move to a newer kit, resync from that kit version; the diff of the resync PR is the whole upgrade.
- Spec schemas and validators reach the project as a **deliberate copy** in `.github/spec-lint/` (no link to the kit in CI — the kit repo may not even exist at CI time). Update: `sync-project.sh <repo>`; divergence detectable with `sync-project.sh --check`. The same sync maintains `CLAUDE.md` and `.claude/settings.json`. Reusable workflows **between repos of the same product** (e.g.: `<product>-client` → `<product>-docs/.github/workflows/reusable-ci-*.yml`) are allowed — what is avoided is depending on the kit.
- Legacy archive originals: only reports/manifests enter the repo (project rule, in the project's `docs/legacy/README.md`).
