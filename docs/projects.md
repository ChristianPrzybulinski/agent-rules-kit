# What lives in a project that uses the kit

Rules, skills, references and templates are authored **in the kit** under `plugins/` and reach the agent through the plugin marketplaces or `bootstrap.sh`. The project receives its own artifacts plus generated, version-stamped copies (table below).

## In the project

| Artifact | Origin in the kit | Example (a docs repository) |
|---|---|---|
| repo `AGENTS.md` | `plugins/guardrails/templates/project-agents-*.md` filled in | `AGENTS.md` (scope, commands, boundaries) |
| `docs/spec/` | created by `platforms/kits/sdd/init-spec.sh`; artifacts follow `plugins/guardrails/templates/spec-*` and `platforms/ci/schemas/` schemas; `spec.md` carries the project's `sdd:` process parameters (`plugins/guardrails/skills/sdd-constitution/references/sdd-parameters.md`, KIT-067) | `docs/spec/spec.md`, `needs/NEED-0nn-slug.md`, `features/FEAT-0nn.md`, `requirements/`, `decisions/`, `debts/` |
| `docs/sessions/` | `plugins/guardrails/templates/doc-session-handoff.md` | `docs/sessions/2026-09-30-initial-specs.md` |
| `docs/legacy/` (or reports) | `plugins/*/templates/doc-*.md` | `docs/legacy/evidence.md` etc. |
| `.github/spec-lint/` | copy generated by `platforms/tools/sync-project.sh` (`check_spec.py` + schemas + `KIT_VERSION`; `spec_trace.py` with journeys; `check_docs_structure.py` while `sdd.doc_structure.enabled`, KIT-074) | local spec validation in the project's CI |
| `.claude/rules/<plugin>-<rule>.md` | generated by `platforms/tools/sync-project.sh` from `plugins/<plugin>/rules/` for the repo profile, marker line names the source and kit version; a `<profile>:<dir>` entry prefixes with `<dir>/` the globs of the rule named after the profile (`godot:client` scopes `dev-godot.md`, never `dev-java.md`) | path-scoped rules for Claude Code in cloud sessions, CI and new machines |
| path-rule block in a folder's `AGENTS.md` | generated by `platforms/tools/sync-project.sh` from the same rendered rules, one block per folder a rule's globs start in, between `agent-rules-kit: path rules` markers; `spec.md` `sdd.rule_paths` moves a rule to other folders (KIT-067) | the rules for Codex and other runtimes that load no rule by path; the root block also reaches Claude Code through `CLAUDE.md` |
| `kit.just` (and `kit-<profile>.just` where one folder has several profiles) + the folder's `justfile` | generated by `platforms/tools/sync-project.sh` (`sync_just.py`) from `platforms/kits/just/<profile>.just` in each profile folder, marked on its first line; the folder's `justfile` is the project's own and imports it (`import 'kit.just'`), and the sync writes a starter one only where none exists (KIT-074) | `just verify` in `server/`, the same recipe CI runs |
| `.github/merge-drivers/keyed_csv_merge.py` | copy of `platforms/kits/godot/scripts/keyed_csv_merge.py` for a godot profile, generated by `platforms/tools/sync-project.sh`; the `.gitattributes` line (`<csv> merge=keyed-csv`) is the project's, the `git config merge.keyed-csv.driver` step is each clone's (KIT-074) | translation CSVs merged by key |
| `CLAUDE.md` | generated by `platforms/tools/sync-project.sh`: a marker comment plus `@AGENTS.md` (`AGENTS.md` stays the single source) | same content on Claude Code before 2.1.277, in the GitHub Action and in cloud sessions |
| `.claude/settings.json` | generated by `platforms/tools/sync-project.sh`: `extraKnownMarketplaces.ai-kit`, `includeGitInstructions: false` (KIT-071) and `enabledPlugins`: `guardrails@ai-kit: true` in plugins mode; in vendored mode `guardrails@ai-kit: false`, `guardrails-pinned@skills-dir: true` and `hooks` entries that run `.claude/ai-kit/hooks/` (KIT-072); other keys and the project's own hooks preserved | each collaborator's local Claude Code loads the kit once, from the plugin install or from the pin |
| `.claude/ai-kit/hooks/` | vendored mode only (KIT-072): each hook of `plugins/guardrails/hooks/hooks.json` as a script, plus `hooks.json`, the settings fragment that runs them through `${CLAUDE_PROJECT_DIR}`, written by `platforms/tools/sync_pinned_plugin.py`, marker `.agent-rules-kit` | the guard and the other kit hooks at the project's kit version, in every session at the repository root, trusted or not and under `claude -p` |
| `.claude/ai-kit/platforms/` | vendored mode only (KIT-072): every kit file the skills, rules, agents or templates call as `~/.ai-kit/platforms/<path>` (`review_checks.py`, `complexity.py`, `spec_trace.py`, the Compose template, …) plus the kit modules those tools import, written by `platforms/tools/sync_pinned_plugin.py`; the vendored skill copies and rules call them as `"$(git rev-parse --show-toplevel)"/.claude/ai-kit/platforms/<path>` | the tools at the project's kit version, from any folder of the checkout and in every runtime |
| `.claude/skills/<name>/` + `KIT_MANIFEST.json` | copy of `plugins/<plugin>/skills/<name>/` for the repo profile, generated by `platforms/tools/sync-project.sh --vendor-skills`, marker `.agent-rules-kit`, sha256 per file in the manifest; the manifest also records the profile list, which a sync without `--profile` reuses, and the pin: `KIT_VERSION`, `KIT_COMMIT`, the hashes of `.claude/skills/guardrails-pinned/` and `.claude/ai-kit/` and `copies`, the hash of each `.github/spec-lint/` file (KIT-072) | skills in Claude Code cloud sessions, the GitHub Action, Devin Cloud and new machines |
| `.claude/skills/guardrails-pinned/` | vendored mode only (KIT-072): the agents, templates and every skill of `plugins/guardrails/` not copied as a plain `.claude/skills/<name>/`, at the synced version, written by `platforms/tools/sync_pinned_plugin.py`, marker `.agent-rules-kit`; agent preloads name `guardrails-pinned:<skill>` or the plain copy | the subagent profiles and the always-on skills at the project's kit version, loaded by Claude Code as `guardrails-pinned@skills-dir` once the main checkout root is trusted |
| `.github/workflows/` | `platforms/kits/github/workflows/` | `docs-checks.yml` (runs the local copy — no kit checkout/token; any filename works, `sync-project.sh` detects it by content), `gitleaks.yml`, `reusable-ci-*.yml` |
| `.github/PULL_REQUEST_TEMPLATE.md`, `CODEOWNERS`, `dependabot.yml`, labels, root `REVIEW.md` | `platforms/kits/github/` | ditto + `scripts/labels-sync.sh`; `REVIEW.md` is copied to the repository root, not to `.github/`, by `sdd-constitution` § 5, which removes the lines a project gate enforces |
| `infra/` / compose | `platforms/kits/docker/` | `infra/compose.yml` (`name: <project>`) |
| `.gitattributes` (LFS) | `platforms/kits/git-lfs/` | the repo's first commit |

IDs in `docs/spec/`: `NEED-nnn`, `FEAT-nnn`, `REQ-F-nnn`, `REQ-NF-nnn`, `DEC-nnn` (or one prefix per decision kind that `spec.md` `decision_kinds` declares), `DEBT-nnn` — sequential numbering, `id` = the file name's prefix, status in frontmatter (`proposed`/`approved`/`delivered`…). Process: `plugins/guardrails/skills/sdd-constitution/references/sdd-process.md`.

## What does NOT go to the project

- Skills stay in the kit and reach the machine through the plugin install; a project may vendor the skills of its profile into `.claude/skills/` with `platforms/tools/sync-project.sh --vendor-skills` (never by hand), like the generated `.claude/rules/` copies in the table above. Knowledge is not copied.
- Spec schemas and validators reach the project as a **deliberate copy** in `.github/spec-lint/` (no link to the kit in CI — the kit repo may not even exist at CI time). Update: `sync-project.sh <repo>`; divergence detectable with `sync-project.sh --check`. The same sync maintains `CLAUDE.md` and `.claude/settings.json`. Reusable workflows **between repos of the same product** (e.g.: `<product>-client` → `<product>-docs/.github/workflows/reusable-ci-*.yml`) are allowed — what is avoided is depending on the kit.
- Legacy archive originals: only reports/manifests enter the repo (project rule, in the project's `docs/legacy/README.md`).

## Pinning the kit version (KIT-072)

A vendored project uses the kit version it last synced, in every local Claude Code session started at its root. The plugin install cannot pin per project: Claude Code keeps one `ai-kit` marketplace clone per user and one plugin cache directory per version (`~/.claude/plugins/cache/ai-kit/guardrails/<version>/`), and the kit's manifest version stays the same between releases, so `refresh.sh` rewrites that directory after each kit merge. The vendored sync therefore writes the kit hooks into `.claude/ai-kit/hooks/` and runs them from `.claude/settings.json` `hooks`, copies the agents and the skills not vendored plain into `.claude/skills/guardrails-pinned/` and, once both are written, turns `guardrails@ai-kit` off for the project; a kit merge changes nothing there until the next `sync-project.sh` run, and the resync PR is the version bump.

The tools travel with the pin too. The kit text calls a tool or template as `~/.ai-kit/platforms/<path>` (or `$HOME/.ai-kit/platforms/<path>`, rewritten without the inner quotes so a double-quoted call stays one word), the kit clone; in a vendored project the sync copies each such file (and the kit modules it imports) into `.claude/ai-kit/platforms/` and rewrites the call in every vendored skill copy, rule and `AGENTS.md` block to `"$(git rev-parse --show-toplevel)"/.claude/ai-kit/platforms/<path>`. `git rev-parse` resolves the checkout from any subfolder (a Godot tool runs from the Godot project folder) and in every runtime; `${CLAUDE_PROJECT_DIR}` would not, since Claude Code substitutes it only in a `SKILL.md` body and other runtimes not at all. A repository in plugins mode, or one never synced, keeps `~/.ai-kit/` as the fallback, and `~/.ai-kit/plugins/` (a kit proposal edits the kit source) stays as written. The location line under each rendered rule and the `AGENTS.md` path-rule block name `.claude/skills/guardrails-pinned/skills/<skill>/` for a skill not vendored plain.

Claude Code runs hooks from a settings file in a folder it does not trust and under `claude -p`, but loads a skills-directory plugin only in a trusted folder (docs `permissions`, the trust table): the guard therefore never depends on trust, while the pinned skills and agents appear once the main checkout root is trusted.

`sync-project.sh --check` reports a pinned file or `.github/spec-lint/` copy that differs from `KIT_MANIFEST.json`, a `kit_files()` entry the pin lacks, settings that drop the kit hooks or re-enable `guardrails@ai-kit` (`settings.local.json` included) and, with `AI_KIT_CLAUDE_PROBE=1`, what `claude plugin list` shows for the repository: no `guardrails-pinned@skills-dir` there fails the check, since the folder is not trusted. `doctor.sh` warns about each project that vendors kit copies but still loads `guardrails@ai-kit`, and about each pinned checkout whose main checkout root is not trusted.

The user install is pinned to a release tag, not per project (#271): `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md` (the always-on `AGENTS.md`) link into the `~/.ai-kit` clone, which `refresh.sh` keeps detached at the newest `vX.Y.Z` on `origin/main`; the Codex marketplace uses that tag as its `ref`; Devin's team plugin must name it in Customize → Plugins → Plugin settings → Edit manifest, which no CLI sets. `doctor.sh` fails when any of the three is not at that release. One always-on file serves every project on the machine, so a project cannot hold its own version of it; a vendored project that syncs from a newer kit than the machine's release reads the older always-on file until the next release.

Not pinned, each for a reason: the Claude Code plugin of a repository in plugins mode. A Claude Code marketplace takes a ref (`claude plugin marketplace add <owner>/<repo>#<tag>`, measured on 2.1.287), but an added marketplace keeps its source, so a new ref is a remove and an add, and `claude plugin marketplace remove` uninstalls the kit plugin and deletes its data (the rule-load log); until a ref change without that loss exists (#271 stays open for it), plugins mode follows `main`, and a project that needs a pinned kit vendors it. Also not pinned: a session started in a subfolder (Claude Code reads the project's `.claude/settings.json` and repository plugins from the session's starting folder only); and a desktop-app worktree, which loads the repository plugin from the main checkout.

Migration for a vendored project from before KIT-072:

1. Run `platforms/tools/sync-project.sh <repo>` from the kit version to pin (the manifest keeps the vendored mode and profile). It writes `.claude/ai-kit/hooks/` and `.claude/skills/guardrails-pinned/`, adds the kit hooks to `.claude/settings.json`, sets `guardrails@ai-kit` to `false` and `guardrails-pinned@skills-dir` to `true`, and records `KIT_COMMIT`.
2. Commit the result in one PR; `sync-project.sh --check <repo>` passes on it.
3. Remove anything that writes `guardrails@ai-kit: true` back into the project's `.claude/settings.json`, such as `claude plugin install guardrails@ai-kit --scope project` in a worktree script; a `.claude/settings.local.json` that enables it loads the kit head beside the pin.
4. Start `claude` at the main checkout root and accept the trust dialog there once; a trusted parent folder or a `claude -p` run does not count.
5. In a session at the repository root run `/plugin` (or `claude plugin list` there): `guardrails-pinned@skills-dir` is enabled, `guardrails@ai-kit` disabled, and each kit skill appears once.
6. To move to a newer kit, resync from that kit version; the diff of the resync PR is the whole upgrade.
