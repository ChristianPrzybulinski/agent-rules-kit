# What lives in a project that uses the kit

Rules, skills, references and templates are authored **in the kit** under `plugins/` and reach the agent through the plugin marketplaces or `bootstrap.sh`. The project receives its own artifacts plus generated, version-stamped copies (table below).

## In the project

| Artifact | Origin in the kit | Example (a docs repository) |
|---|---|---|
| repo `AGENTS.md` | `plugins/guardrails/templates/project-agents-*.md` filled in | `AGENTS.md` (scope, commands, boundaries) |
| `docs/spec/` | created by `platforms/kits/sdd/init-spec.sh`; artifacts follow `plugins/guardrails/templates/spec-*` and `platforms/ci/schemas/` schemas; `spec.md` carries the project's `sdd:` process parameters (`plugins/guardrails/skills/sdd-constitution/references/sdd-parameters.md`, KIT-067) | `docs/spec/spec.md`, `needs/NEED-0nn-slug.md`, `features/FEAT-0nn.md`, `requirements/`, `decisions/`, `debts/` |
| `docs/sessions/` | `plugins/guardrails/templates/doc-session-handoff.md` | `docs/sessions/2026-09-30-initial-specs.md` |
| `docs/legacy/` (or reports) | `plugins/*/templates/doc-*.md` | `docs/legacy/evidence.md` etc. |
| path-rule block in a folder's `AGENTS.md` | generated by `platforms/tools/sync-project.sh` from `plugins/guardrails/rules/` for the repo profile (`plugins/guardrails/hooks/sync-profiles.txt`), one block per folder a rule's globs start in, between `agent-rules-kit: path rules` markers; a `<profile>:<dir>` entry prefixes with `<dir>/` the globs of the rule named after the profile (`godot:client` scopes the godot rule, never the java one), and `spec.md` `sdd.rule_paths` moves a rule to other folders (KIT-067) | the rules for Codex and other runtimes that load no rule by path; the root block also reaches Claude Code through `CLAUDE.md` |
| the import line in each profile folder's `justfile` | `import '~/.ai-kit/platforms/kits/just/<profile>.just'`, written by `platforms/tools/sync-project.sh` (`sync_just.py`) into a starter `justfile` or in place of an older `import 'kit.just'` line; the rest of the `justfile` is the project's own, and the module stays in the kit (KIT-074; KIT-081 stage 1b, below) | `just verify` in `server/`, the same recipe CI runs |
| the `.gitattributes` line `<csv> merge=keyed-csv` | the project's; each clone runs the printed `git config merge.keyed-csv.driver` step once, which runs the installed kit's `platforms/kits/godot/scripts/keyed_csv_merge.py` (KIT-074; KIT-081 stage 1b: no copy) | translation CSVs merged by key |
| `CLAUDE.md` | generated by `platforms/tools/sync-project.sh`: a marker comment plus `@AGENTS.md` (`AGENTS.md` stays the single source); the marker records the kit version and the profile list, which a sync without `--profile` reuses (`<!-- generated by agent-rules-kit sync-project.sh v<version>; profile docs,godot:client; AGENTS.md is the source -->`, KIT-081 stage 2b) | same content on Claude Code before 2.1.277, in the GitHub Action and in cloud sessions; the marker also turns on the plugin's path-rule hook and its profile list selects the rules (KIT-081 stage 3) |
| `.claude/settings.json` | generated by `platforms/tools/sync-project.sh`: `extraKnownMarketplaces.ai-kit` (the kit repository at `"ref": "stable"`, KIT-081), `includeGitInstructions: false` (KIT-071) and `enabledPlugins`: `guardrails@ai-kit: true`; other keys and the project's own hooks preserved | each collaborator's local Claude Code loads the kit once, from the plugin install |
| `.github/workflows/` | `platforms/kits/github/workflows/`; `spec-lint.yml` is written by `platforms/tools/sync-project.sh` when no workflow runs the spec tools, with the spec-tools action pinned to the kit commit (KIT-081 stage 1) | `spec-lint.yml` or `docs-checks.yml` (runs `ChristianPrzybulinski/agent-rules-kit/platforms/ci/actions/spec-tools@<SHA>  # vX.Y.Z`; any filename works, `sync-project.sh` detects it by content), `gitleaks.yml`, `reusable-ci-*.yml` |
| `.github/PULL_REQUEST_TEMPLATE.md`, labels, root `REVIEW.md` | `platforms/kits/github/` | ditto + `scripts/labels-sync.sh`; `REVIEW.md` is copied to the repository root, not to `.github/`, by `sdd-constitution` § 5, which removes the lines a project gate enforces |
| `infra/` / compose | `platforms/kits/docker/` | `infra/compose.yml` (`name: <project>`) |
| `.gitattributes` (LFS) | `platforms/kits/git-lfs/` | the repo's first commit |

IDs in `docs/spec/`: `NEED-nnn`, `FEAT-nnn`, `REQ-F-nnn`, `REQ-NF-nnn`, `DEC-nnn` (or one prefix per decision kind that `spec.md` `decision_kinds` declares), `DEBT-nnn` — sequential numbering, `id` = the file name's prefix, status in frontmatter (`proposed`/`approved`/`delivered`…). Process: `plugins/guardrails/skills/sdd-constitution/references/sdd-process.md`.

## What does NOT go to the project

- Skills, agents and hooks stay in the kit and reach the machine through the plugin install; no sync copies them into the project (KIT-081 stage 2b, below). Knowledge is not copied.
- Path rules stay in the kit (KIT-081 stage 3, below): the plugin's hook gives Claude Code each rule when a tool call reads or edits a matching file; no `.claude/rules` copy.
- The `just` modules and the keyed-CSV merge driver stay in the kit (KIT-081 stage 1b): the justfile imports the installed kit's module and git runs the installed kit's driver.
- Spec schemas and validators stay in the kit (KIT-081 stage 1): a session runs them from the installed kit, `${AI_KIT_DIR:-$HOME/.ai-kit}/platforms/ci/`, and the project's CI through the spec-tools composite action pinned to a kit commit by SHA (below). The sync maintains `CLAUDE.md` and `.claude/settings.json`. Reusable workflows **between repos of the same product** (e.g.: `<product>-client` → `<product>-docs/.github/workflows/reusable-ci-*.yml`) are allowed — what is avoided is depending on the kit.
- Legacy archive originals: only reports/manifests enter the repo (project rule, in the project's `docs/legacy/README.md`).

## The spec tools run from the kit (KIT-081 stage 1)

Until stage 1, `sync-project.sh` copied `check_spec.py`, `row_checks.py`, `pr_gates.py`, `spec_trace.py`, `check_docs_structure.py` and the schemas into the project's `.github/spec-lint/`, with `KIT_VERSION`, and the project's CI ran that copy; each kit release needed a project PR that rewrote it. Now:

- A session runs the installed kit's validators: the skills name `~/.ai-kit/platforms/ci/validations/<tool>` with `~/.ai-kit/platforms/ci/schemas`, and the post-edit hook and the `docs.just` `lint` recipe use `${AI_KIT_DIR:-$HOME/.ai-kit}`.
- The project's CI runs them through the composite action `platforms/ci/actions/spec-tools` (its README lists the inputs), referenced as `uses: ChristianPrzybulinski/agent-rules-kit/platforms/ci/actions/spec-tools@<40-character SHA>  # vX.Y.Z`: the scripts and schemas come with the pinned commit, and nothing else is fetched. The action also exports `AI_KIT_DIR` for later steps (`just lint`, `pr_gates.py`). Dependabot or Renovate bumps the line when the kit releases and merges it on green CI (option B of the KIT-081 record; `platforms/kits/github/README.md` has the configuration).
- `sync-project.sh` writes `.github/workflows/spec-lint.yml` (or the `--workflow` name) only when no workflow runs the spec tools, pinned to the kit commit it runs from, and never overwrites a file. It removes a generated `.github/spec-lint/`: only when its `README.md` carries the generated heading, and only the kit-named files; any other file stays with a `sync: kept` line, and a symbolic link is never followed. `--check` fails on a generated copy left and on each workflow line that names `.github/spec-lint/`, with its `file:line` and the fix.

Migration for a project that has the copy:

1. Run `platforms/tools/sync-project.sh <repo>` once from a kit with stage 1, from `~/.ai-kit` so the pin is a release. It removes the copy and, when no workflow runs the spec tools, writes `spec-lint.yml`.
2. Replace each workflow step the sync names (`sync: warning: <file>:<line> names .github/spec-lint/`) with the action, pinned by SHA (`checks: spec,trace,rows` covers `check_spec.py`, the doc-structure check, the baseline, `spec_trace.py check` and the row checks), or run another kit tool after it from `$AI_KIT_DIR`, such as `spec_trace.py sync-status --write`.
3. Add the Dependabot or Renovate entry that bumps the pin, and commit everything in one PR; `sync-project.sh --check <repo>` passes on it.

## Changelog fragments, the status-sync pull request and the secret scan (KIT-084)

A project that keeps `changelog.d/<id>.<type>.md` fragments runs the kit's `platforms/ci/validations/changelog_fragments.py` from the installed kit (`just changelog`, `just changelog --check` in a justfile that imports the `docs` module), and its CI copies the `changelog-consolidate.yml` template, which runs the tool from `$AI_KIT_DIR` after the spec-tools action and opens one pull request. A spec with `sdd.tracker: github` copies `spec-status-sync.yml`, which does the same with `spec_trace.py sync-status --write`. Both templates run on dispatch only and need the `PR_BOT_TOKEN` secret (`platforms/kits/github/README.md` lists its permissions); no tool or body file is copied into the project. The secret scan is the kit's gitleaks action, `platforms/ci/actions/gitleaks`, pinned by SHA as a step of any job or through the `gitleaks.yml` template, which calls it.

## The just modules and the merge driver run from the kit (KIT-081 stage 1b)

Until stage 1b, `sync-project.sh` wrote each profile's module into its folder as `kit.just` (a folder with several profiles got `kit-<profile>.just` modules and a `kit.just` that ran their shared recipes) and copied the keyed-CSV merge driver into `.github/merge-drivers/`. Now:

- The justfile of each profile folder holds `import '~/.ai-kit/platforms/kits/just/<profile>.just'`. just 1.58.0 replaces a leading `~/` in an import path with the home folder and runs an imported recipe in the importing justfile's folder; an import path is a fixed string, so it cannot read `AI_KIT_DIR`. The sync writes that line into a starter `justfile`, or in place of an `import 'kit.just'` line whose `kit.just` it generated; a justfile without it is a warning, and a `--check` failure naming the line to add. A folder with several profiles gets no import and a warning, since a `mod` module's recipes run in the kit's folder and two imports define the same recipe names.
- In CI, the spec-tools action links `$HOME/.ai-kit` to the kit at the commit it pins, unless a kit is already there, which must be at that commit or the step fails (KIT-083); a job that runs `just` calls it with `checks: none` before its first `just` step, as `ci-godot.yml` and `ci-java.yml` do.
- The printed `git config merge.keyed-csv.driver` step runs `python3 ~/.ai-kit/platforms/kits/godot/scripts/keyed_csv_merge.py`; `.gitattributes` stays the project's.

Migration for a project that has the copies:

1. Run `platforms/tools/sync-project.sh <repo>` once from a kit with stage 1b. It rewrites each `import 'kit.just'` line to the kit module's import in place, removes each `kit.just` and `kit-<profile>.just` whose first line carries the generated marker and the vendored `.github/merge-drivers/keyed_csv_merge.py`, and keeps an unmarked file with a `sync: kept` line; nothing is read or removed through a symbolic link.
2. Run the printed `git config merge.keyed-csv.driver` line once in each clone (`--check` fails while the clone's config still runs the removed copy).
3. Add the spec-tools step with `checks: none` before the first `just` step of each project CI job that runs a recipe, and commit everything in one PR; `sync-project.sh --check <repo>` passes on it.

## No kit copies in the project (KIT-081 stage 2b)

A project uses the `guardrails@ai-kit` plugin the machine installed, which follows the kit's `stable` branch, so a kit merge reaches no project until a release moves `stable` (KIT-081 stage 2a). Until stage 2b a project could pin its own kit version instead (`sync-project.sh --vendor-skills`, KIT-072): plain skill copies in `.claude/skills/<name>/`, the rest of the plugin as `.claude/skills/guardrails-pinned/`, the kit hooks and tools in `.claude/ai-kit/`, `.claude/skills/KIT_MANIFEST.json`, and `.claude/settings.json` hooks that ran the pinned scripts with `guardrails-pinned@skills-dir` on and `guardrails@ai-kit` off. That pin existed because the plugin followed `main`; with `stable` its reason is gone, and each kit release no longer needs a resync PR per project.

`--vendor-skills` now exits 2. `sync-project.sh <repo>` migrates a repository that still holds that state (`platforms/tools/sync_unvendor.py`): after it has turned `guardrails@ai-kit` on and written the profile list into the `CLAUDE.md` marker, it removes each folder that carries the generated `.agent-rules-kit` marker, `KIT_MANIFEST.json`, the `.claude/settings.json` hook handlers that run `.claude/ai-kit/hooks/` and the `guardrails-pinned@skills-dir` key, printing one line per removal. The project's own hooks, keys and skills stay: an unmarked folder or a symbolic link is never read, replaced or deleted, and the sync names each one it kept where the manifest or the pin expected a kit folder. `sync-project.sh --check` fails while any of that state is left, naming each path and the sync that removes it, and `doctor.sh` warns about each checkout Claude Code records an `@ai-kit` install for that still holds it.

The profile list moves with it: a sync without `--profile` takes the list the `CLAUDE.md` marker records, else the one `KIT_MANIFEST.json` records (a vendored repository's first migration run), else infers it; the run prints the source (`sync: profile=<list> (--profile|CLAUDE.md|manifest|inferred)`).

Migration for a vendored project:

1. Run `platforms/tools/sync-project.sh <repo>` once from a kit with stage 2b. It keeps the profile list from `KIT_MANIFEST.json`, writes it into `CLAUDE.md`, enables `guardrails@ai-kit` and removes the copies, the pin and the pin's settings entries.
2. Commit the result in one PR; `sync-project.sh --check <repo>` passes on it.
3. Remove what pinned the project by hand, if anything: a `.claude/settings.local.json` that sets `guardrails@ai-kit` to `false` or names `guardrails-pinned@skills-dir`, or a worktree script that writes either.
4. In a session at the repository root run `/plugin` (or `claude plugin list` there): `guardrails@ai-kit` is enabled at the machine's release, and each kit skill appears once.

## Path rules from the plugin (KIT-081 stage 3)

Claude Code loads a path rule by itself only from a file in the project's `.claude/rules/`, so until stage 3 `sync-project.sh` rendered each rule the profile receives into `.claude/rules/<plugin>-<rule>.md`. The `guardrails` plugin now gives the rule: its PostToolUse hook `plugins/guardrails/hooks/path_rules.py` runs after Read, Edit, Write, MultiEdit, NotebookEdit, Bash and Grep, and when the call names a file a rule's `paths` globs match (for Bash, the path-like words of the command), it adds the rule to the session once, as context next to the tool result.

- It acts only in a project whose `CLAUDE.md` starts with the sync marker, so the user-scope plugin gives no rule in any other repository.
- The marker's profiles select the rules through `plugins/guardrails/hooks/sync-profiles.txt`, the same map the copies used.
- The globs are the kit's own: the `<profile>:<dir>` and `sdd.rule_paths` scopes only narrowed the copies, and they still shape the `AGENTS.md` blocks.
- Each delivery adds a `kit_hook_path_match` line to the plugin's rule-load log, which `platforms/tools/skill_usage.py --rules` counts per rule.

The `AGENTS.md` blocks stay: Codex reads only `AGENTS.md`, and a way to give Codex a rule without a file in the project waits for a Codex probe.

Migration: run `platforms/tools/sync-project.sh <repo>` once from a kit with stage 3. It writes the `CLAUDE.md` marker first, then removes each `.claude/rules/*.md` that carries the generated `<!-- agent-rules-kit: generated from` line, one `sync: removed` line each, and names the project's own rules it kept (`sync: kept`); it reads and removes nothing through a symbolic link. `sync-project.sh --check` fails while a kit-marked copy is left and names it. Commit the result in one PR.

The user install is pinned to a release, not per project (#271): `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md` (the always-on `AGENTS.md`) link into the `~/.ai-kit` clone, which `refresh.sh` keeps detached at the newest `vX.Y.Z` on `origin/main`. The Claude Code and Codex marketplaces and Devin's team plugin follow the `stable` branch, which `release.yml` moves to each release (KIT-081): the marketplaces name `#stable` / `--ref stable` once, and Devin's team plugin names `stable` in Customize → Plugins → Plugin settings → Edit manifest, which no CLI sets. `doctor.sh` fails when the clone is not at the newest release or any of the three refs is not `stable`. One always-on file serves every project on the machine, so a project cannot hold its own version of it.

The Claude Code plugin of a synced repository follows the release too (KIT-081): the user's marketplace is `<owner>/<repo>#stable`, and the project's `.claude/settings.json` declares the same source with `"ref": "stable"` (`sync-project.sh` writes it, and `--check` reports a source without it), because a project-declared source that differs from the user's conflicts with it. Claude Code 2.1.287 keeps a marketplace's ref with its source, so the one move per machine from `main` is a remove and an add, and `claude plugin marketplace remove` uninstalls the kit plugin and deletes its data (the rule-load log); `refresh.sh` backs that data up first and restores it after the install. Between a tag and the `release.yml` run that moves `stable`, the plugin's skills can lag the always-on file by one release. A session started in a subfolder does not read the project's `.claude/settings.json` (Claude Code reads it from the session's starting folder only, KIT-072), so it loads the user's `guardrails@ai-kit`, which follows `stable` too.
