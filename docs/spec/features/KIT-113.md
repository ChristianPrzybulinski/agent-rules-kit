# KIT-113 — Let an unanswered owner question wait only at the merge

## Problem and evidence

[FACT] Skills `sdd-clarify` § 2 and `sdd-plan` § 5 stop the step at an owner question: the plan cannot reach `planned`
with a choice open and no later step starts. Measured in the Stratics architect session of 2026-11-18 (issue #389,
kit 17.1.0 to 18.0.0): one plan question (dev-game-studio/stratics#4781) stayed open from 03:30:54 to 09:37:22 UTC,
366.5 of the 482.1 minutes from request to the first cut issue (76 %); another (#4780) 369.8 of 556.1 minutes. Both came
2 to 4 minutes after the owner's last answer of the night, with the owner away; no session sent a push notification,
because the project rule that says to push when blocked lives outside the kit. 26.1 minutes of work were still left
after the answer.

[FACT] `check_spec.py` already reads every Markdown file under the spec dir for merge-conflict markers
(`check_conflict_markers`), so a line a spec must not carry into `main` has a failing rule today. The merge block of
this FEAT rests on the same mechanism, not on prose (the coordinator decided that the issue's "optional enforcement"
is required).

## Scope

- `plugins/guardrails/skills/sdd-clarify/SKILL.md` § 2 and `plugins/guardrails/skills/sdd-plan/SKILL.md` § 5 (the
  only part of `sdd-clarify` this FEAT touches): an owner question unanswered for `sdd.owner_wait_minutes` does not
  stop the step; notify the owner once through the runtime's push tool if it has one, continue on the marked
  recommendation, write `[DECISION] pending owner: <option> (asked YYYY-MM-DD HH:MM UTC)` as a line of its own in the
  artifact the step shapes, finish the chain in the same branch and stop before the merge; the spec PR lists every
  pending decision first; never merge with one. A question whose answer does not depend on a long run is asked before
  that run.
- `platforms/ci/schemas/profile.schema.json`: key `sdd.owner_wait_minutes`, integer, minimum 1, default 10,
  `x-read-by: sdd`; `plugins/guardrails/skills/sdd-constitution/references/sdd-parameters.md`: its row.
- `platforms/ci/validations/check_spec.py`: rule `pending-decision` (added to `RULES`) fails a line that starts with
  the marker (after at most list, quote, numbering, checkbox, heading, table-cell or bold markers, in any case and
  spacing) in any Markdown file under the spec dir, naming `file:line`; the same text quoted inside running text
  passes. The owner's answer rewrites the line to `[DECISION] <option>, chosen by the owner on YYYY-MM-DD`, which
  passes, and then folds as usual; the skills name that rewrite as the one edit the fold rule allows.
- `platforms/ci/validations/test_check_spec.py` (`PendingDecisionTest`; the key's default and minimum in
  `SddParamsTest`) and `platforms/ci/validations/test_profile.py` (the `sdd` key count, 31 to 32);
  `platforms/ci/README.md`: one clause on the rule; `CHANGELOG.md`.
- Issue #390 ships in the same PR, text only (the front chain's second cut, one spec PR per NEED):
  `sdd-constitution/references/sdd-process.md` § Flow gains the paragraph the issue proposes and `sdd-plan` § 1 reads
  the refined NEED "on the main branch or in this branch"; at the coordinator's request `sdd-plan` § 6 also words the
  full-scope check as #388 changes `sdd-check` (the functional items only on what changed since the NEED's `refined`
  commit, one full run per scope and change). It needs no FEAT record (`.github/CONTRIBUTING.md`
  § Adding content); CA-6 pins its two lines.

## Out of scope

- `sdd-clarify` § 3, `sdd-check`, `sdd-intake`, `sdd-specify` and `sdd-tasks`: other changes edit them.
- Sending the push notification: the runtime's tool does it; the kit only says when to use it.
- A project's own merge gate: its spec check already runs `check_spec.py`, so the rule is its gate; the project
  resolves the line in the PR once the owner answers.
- No release: the owner decides the version (a MINOR change, since it adds a profile key and a spec rule).

## Plan

### Tests

`PendingDecisionTest` was written first and failed on the old `check_spec.py` (three of its five tests: a plain line, a
list item and a line in a journey exited 0); the other two (no line, a non-pending line) passed before and after, as
negatives must. The key's default, a value set and the minimum extend `SddParamsTest` (red first: six failures before
the schema key); adding the key moves `test_the_sdd_section_is_the_only_home_of_the_process_parameters` from 31 to 32
keys. The skill text is a prose change with no executable behavior of its own: its proof is CA-4 and CA-6 (greps) and
`check.sh` (line limits, descriptions). Evals: no trigger bullet and no skill description changes, so
`.github/CONTRIBUTING.md` § Evals asks for no run; the six `trigger` cases were run by hand anyway (2 runs each, 1.00
each, $2.54), without `--allow-tools` because `~/.docker` holds a symbolic link.

### Risks

- An agent could leave the pending choice in a form the rule does not match (a different wording, or text not at the
  start of a line). The rule matches the marker the skills prescribe; the prose and the review still catch a variant,
  and a line that merely quotes the marker passes by design.
- A recommendation the owner rejects costs rework of the artifacts built on it. The issue's measure applies: if the
  owner picks another option for more than one pending decision in three, or the time from the answer to the first cut
  issue does not fall below 26.1 minutes, revisit the default or the rule.
- The block holds only where the `spec` check runs on the PR and is a required check, and `pending-decision` is not in
  `baseline.json` (`sdd-parameters.md` says so).
- A project's `baseline.json` could hold a `pending-decision` finding. The baseline only shrinks and
  `--baseline-against` fails an added entry, so a new pending line still blocks; `--baseline-init` on a spec that
  already holds one would hide it, which the project sees in the baseline diff.
- The wait is a default the project can change; a value of 1 minute makes the chain proceed almost at once, so a
  project that wants the owner's reply sets a larger number.

## Decisions

- 2026-11-19 (#389): chose 10 minutes as the default of `sdd.owner_wait_minutes`, as the issue proposes, over 5 or 30,
  because a phone reply fits it and both measured waits ran for hours, so any value below an hour recovers the night; a
  project sets its own.
- 2026-11-19 (#389, coordinator): made the `check_spec.py` rule required, not optional, because a merge block that
  rests on a skill sentence fails the first time an agent forgets it, which is the failure this FEAT exists to remove.
- 2026-11-19 (#389): chose to scan every Markdown file under the spec dir, as `check_conflict_markers` does, over only
  FEATs and NEEDs, because the line lands in the artifact the step shapes (a NEED, a REQ, a decision record or a FEAT);
  and to match at the start of a line over any occurrence, so a spec or a skill that quotes the marker does not fail.
- 2026-11-19 (#390): shipped the front-chain text in the same PR as a CHANGELOG line, not as a second FEAT, because it
  is a skill and reference text edit and the two issues are one concern (shortening the chain before the rows).
- 2026-11-19 (review of #410): made the resolved form `[DECISION] <option>, chosen by the owner on YYYY-MM-DD` the one
  edit of a pending line, an exception to the fold rule's "not edited or deleted", because folding the pending line
  keeps the marker and the check could never go green; `pending owner answered` is not that form.
