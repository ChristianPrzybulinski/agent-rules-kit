# KIT-106 — Track each FEAT in one GitHub issue

## Problem and evidence

[FACT] The owner requested in Codex on 2026-11-18: "Crie mais uma melhora no kit, hoje ele separa em tasks uma feat e crie N issues, vamos mudar para: 1 FEAT = 1 ISSUE ele pode trr a tabela de tasks no arquivo da feat mas nao tem pq quebrarmos tanto" (issue #398).

[FACT] At base `9ebf878`, `sdd-tasks` cuts one issue per task/bundle and an optional separate FEAT card. `spec_trace.py sync-status` applies an issue's state to every row that names it. Pointing all rows to one issue without changing synchronization would falsely complete or block unrelated rows.

[DECISION] Type: platform; route: feat-only; size: M; priority: now; confirmed by: owner, 2026-11-18, the request above. Keep execution detail in the FEAT and reduce GitHub tracking to one issue. Existing issue history is preserved; a failed/ambiguous create must not produce duplicates.

## Scope

- `plugins/guardrails/skills/sdd-tasks/SKILL.md` and its `references/task-issue.md`, `references/task-cut.md`: one canonical issue, idempotent creation/resync, row evidence, migration boundary and local TASK compatibility.
- `plugins/guardrails/skills/sdd-implement/SKILL.md`, its `references/task-pr.md`, and `plugins/guardrails/skills/sdd-review/SKILL.md`: row scope and progress, referencing PRs and closure after acceptance.
- `plugins/guardrails/skills/sdd-check/SKILL.md`, `plugins/guardrails/skills/sdd-constitution/references/sdd-process.md`, `plugins/guardrails/skills/sdd-constitution/references/sdd-parameters.md`, `plugins/guardrails/rules/spec.md`: consistent progress authority and local-only bundle limits.
- `plugins/guardrails/templates/spec-feature.md`, `platforms/kits/github/ISSUE_TEMPLATE/task.md`, `platforms/ci/schemas/feature.schema.json`, `platforms/ci/schemas/profile.schema.json`: canonical issue field and compatible template/parameter contract.
- `platforms/ci/validations/spec_trace.py`, `platforms/ci/validations/test_spec_trace_sync_status.py`, `platforms/ci/README.md`: preserve individual row states of a canonical FEAT issue, derive aggregate FEAT status, retain legacy synchronization.

## Out of scope

- Bulk migration, closure or deletion of existing consumer issues, consumer repository edits, or changing the configured PR unit.
- Removing task tables, local tracker TASK files, execution dependencies, row proofs, owner playtests or closure gates.
- Dependency changes, release publication or layout changes.

## Plan

### Tests

[FACT] On the unchanged implementation, the added regression tests failed six assertions: shared-issue state overwrote row states, and a legacy titled issue completed a new row. After the change, all 42 sync-status tests passed, including legacy cases and repeat-run idempotence. Run the surrounding trace/spec suites and unit/contract gates, validate the canonical field with accepted/rejected values, and review the procedural creation/closure scenarios. No synthetic live GitHub issues are needed.

### Risks

[DECISION] A canonical `issue` means task status is evidenced in the FEAT; it does not mean that a shared issue label or merge proves every row. Legacy records without it retain old sync, including `card` alone. A project-specific cutter that still emits task issues must not run; adapting it is a separately scoped project change. Migration preserves historical issues and verified task evidence. PR granularity remains independent, so task PRs must reference rather than close the shared issue.

## Decisions

- 2026-11-18: chose one canonical FEAT issue over larger bundles (still arbitrary issue splits) and removing rows (loses execution scope, dependencies and proof).
- 2026-11-18: retain local TASK files and old task-issue synchronization for compatibility; new GitHub cuts/resyncs follow the one-issue contract.
- 2026-11-18: keep the existing mark-done command and per-row evidence rather than introduce another progress store or infer task completion from one shared issue.
