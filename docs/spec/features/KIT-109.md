# KIT-109 — Fail a CHANGELOG line added under a released version

## Problem and evidence

[FACT] While KIT-103 (#384) was implemented, its branch added two lines under `## [Unreleased]` of `CHANGELOG.md`;
meanwhile `main` published 17.1.0 (#383), which turned `## [Unreleased]` into `## [17.1.0] - 2026-11-17` and left an
empty `## [Unreleased]` above it. `git rebase origin/main` reported success with no conflict and left the branch's lines
inside the released section. Nothing checked it: `check.sh`, the kit's tests and the PR's CI do not read where a
CHANGELOG line sits, so only `bump_version.py`'s empty-`[Unreleased]` refusal would catch it, one release later and far
from its cause. Source: issue #386.

## Scope

- `platforms/tools/check_changelog.py` (new): reads `git diff -U0 <base> HEAD -- CHANGELOG.md` and fails each added
  line whose section heading is not `## [Unreleased]`, naming the line and the section. A section whose heading the diff
  adds (a release in progress) passes. The base is `--base`, else the merge base with `origin/main`, else `HEAD^1`;
  with none it prints a skip line and passes.
- `platforms/tools/check.sh`: runs it, so CI's `static` job and every local check do.
- `.github/workflows/ci.yml`: the `static` checkout takes `fetch-depth: 2`, so `HEAD^1` (the merge commit's base) exists.
- `platforms/ci/validations/test_check_changelog.py` (new): seven tests (CA-1 to CA-5).
- `platforms/tools/README.md`, `.github/CONTRIBUTING.md`, `CHANGELOG.md`: one line each.
- Amendment (#431): `check_changelog.py` also fails each line of the file at HEAD that opens with a merge-conflict
  marker (`<<<<<<<` or `>>>>>>>`), with or without a base revision; a marker inside running text passes. Test
  `test_a_committed_conflict_marker_fails_with_or_without_a_base`.

## Out of scope

- The optional second step of #386, the same check through the `docs` stack's `changelog --check` recipe for projects
  that set `changelog`: it needs a project profile decision of its own.
- CHANGELOG fragments (`changelog.d/`) for the kit itself, and a line in skill `git` § 4: both rejected in #386.

## Plan

### Tests

`CheckChangelogTest` builds a throwaway git repository per test; CA-3 runs a real `git rebase`. The workflow test
(`test_kit_workflows.py`) must still pass with the `static` checkout change.

### Risks

- A shallow checkout with no `origin/main` and no parent skips the check silently (with a line). CI's `static` job
  checks out two commits for that reason.
- A legitimate edit to a released entry (a typo fix in an old section) fails the check. Fix it in the PR that needs it
  with the release heading's line in the diff, or amend the entry through the `Unreleased` section; the strictness is
  the point of the issue.
- A PR to a branch other than `main` has a different merge base. The kit releases from `main` only.
- On a push to `main`, `HEAD^1` is the base, so a multi-commit push (a rebase-merge, or a direct push of several
  commits) checks only its last commit: a CHANGELOG line added under a released version by an earlier commit of the
  push passes (a false negative). The squash merge the kit uses lands one commit, so it is covered (#405).

## Decisions

- 2026-11-19 (issue #386): chose a script run by `check.sh` over a line in skill `git` § 4, because a command detects
  the mistake without an agent remembering it.
