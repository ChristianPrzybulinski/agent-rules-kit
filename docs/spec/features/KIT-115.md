# KIT-115 — Warn on sibling task rows and on edges inside a set

## Problem and evidence

[FACT] Stratics FEAT-018 and FEAT-112 are cut as 61 `Handler <move>` rows each (two Files per row, every row
`Depends on` one contract row) and FEAT-148 as 34 `Describe ENB-nnn` rows, read in
`stratics-docs/docs/spec/features` on 2026-11-20. The owner's decision of that day is one FEAT, one issue, and a set of
like items cut by what its items share. The kit's prose rule is #428; nothing in `row_checks.py` notices a set.

[FACT] A broader rule, "an edge between two rows that only share a file", was tried on every Stratics FEAT and flagged
239 of 439 edges (54 %), so it is not shipped. Grouping open rows by one title shape fires on exactly FEAT-018 (61 rows)
and FEAT-112 (21 open rows) and on none of FEAT-025, FEAT-032 or FEAT-021, whose rows are distinct capabilities.

## Scope

- `platforms/ci/validations/row_checks.py`: rule `l` (WARN) reports, once per set and on its first open row, four or
  more open rows of one table that share a title shape (the Task cell up to its first `:` or `(`, each backticked name
  and each id or number replaced, the first three words kept, an item token and another word required; an `E2E` and
  a row id such as `T1` are no item, and a lead opening with a sequence word such as `Phase` or `Step` is no set),
  reported on the first of its rows that the check lints; rule `m` (WARN)
  reports a row of such a set whose `Depends on` names another row of the same set. A settled row (`doing`, `blocked`,
  `done`, `cancelled`) is not counted, so a re-cut set keeps its history unflagged. `--strict` promotes `l` and `m`,
  with `c` and `f`, to FAIL. The threshold is the constant `SIBLING_MIN` (4); no profile key.
- `platforms/ci/validations/test_row_checks_sets.py`: the new tests; `plugins/guardrails/skills/sdd-tasks/references/row-checks.md`:
  the two rows of its rule table; `CHANGELOG.md`; `docs/spec/spec.md`: the index row.
- Amendment (#431): a set whose first open row fails rule a is reported on the first of its rows that passes rule a,
  since rule a stops the other rules on its row (`lint` marks `linted` only on such rows); test
  `test_a_set_whose_first_row_fails_rule_a_is_reported_on_the_next`.

## Out of scope

- The prose rule and the re-cut procedure for existing FEATs (`sdd-tasks` § 2 and § 5, #428); the Stratics order of re-cuts is a hand-over note to its architect, not a kit file.
- A rule on edges that only share a file or an area (54 % of Stratics edges: too imprecise to ship).
- The loop's `cut` and its bundling of rows into issues (the review-loop's side).

## Plan

### Tests

`test_row_checks_sets.py` was written with the rules; its first run failed two cases that the design then fixed (a
title that differs only by a number is one shape, by design; `Server E2E of` matched because `E2E` held a digit, so the
id pattern became `(letters-)*[letter]digits` and never matches `E2E`). CA-5 is a measurement on the real tables, run
before and after the id fix.

### Risks

- A false positive: four open rows that look alike and are not a set. The rule is a WARN with a message that names the
  rows, the item token is required and settled rows are not counted; `--strict` is the project's choice to fail on it.
- A set cut with varied titles (no shared first three words) is not found. The prose rule (#428) and the review still
  apply; widening the shape would raise false positives, so the threshold stays until a missed set is shown.
- If new FEATs keep arriving with four or more sibling rows after the warning exists, the warning is ignored: move the
  default to FAIL (the owner's call).

## Decisions

- 2026-11-20 (#429): chose a WARN with `--strict` over a hard FAIL with a profile threshold because FEAT-018, 112, 148
  and 005 would fail at once, which is the mass edit the owner excluded; and chose a title-shape rule over an
  edge-overlap rule because the latter flagged 54 % of Stratics edges.
- 2026-11-20 (#431): kept the glued-backtick shape (``Handler`mN`s``) as it is: cosmetic, and widening the shape
  would raise false positives.
