# KIT-104 — Route a finding where it is found; a NEED only for a need or an owner decision

## Problem and evidence

`sdd-intake` as NEEDs, which then walk intake → specify → clarify → plan. At b5e8306: the always-on bullet
`plugins/guardrails/AGENTS.md:21` ("A new idea, need, improvement or problem … → load skill `sdd-intake` to record
it"), `sdd-constitution/references/sdd-process.md:9` ("every request (idea, need, improvement, problem) is recorded by

type `fix`") and the `spec-process.md` template's Postconditions example ("a fix NEED"); with the trigger case that

## Scope

- `plugins/guardrails/skills/sdd-intake/SKILL.md`: the rule's one home, a new § 4 "Route a finding where it is found".
  A finding (an audit, `sdd-check` on drift the change did not write, `sdd-review`, `sdd-release` acceptance, smoke or
  production, `investigate`, a security scan, a migration) is routed by the agent that found it, by type, first match
  wins, with its evidence (`path:line`, the failing output): fix → a fix task row on the FEAT that owns the code,
  citing the violated artifact's path and the evidence; spec fix (stale or silent text where another approved artifact or a
  recorded owner decision already states what the code does) → in the same change or the area's next spec PR, listed
  for product, an amended REQ, journey or process with a History line, an approved decision only with the owner's
  yes, a new REQ joining the owning FEAT; product choice (the code and an artifact disagree, or nothing states what
  the code does, and either could be right) → one owner question with an example and a recommendation, and only one
  that needs more than one question or is left unanswered becomes a NEED of type `decision`, whose answer § 4 routes
  again; new capability → a NEED. A Fix row bullet places the row (Files first,
  then the violated REQ's FEAT; a `planned`, `in-progress` or `validated` FEAT by resync with a History line and the
  row check, an unplanned one when `sdd-plan` plans it; a delivered FEAT or unowned code through `sdd-plan` § 1); with
  `sdd.flow: feat-only` a fix is its own PR, and with no NEED file a NEED route is a request for `sdd-specify` or an
  issue; the report that found a finding names its route. The description, intro, Rules and Done when name both entries.
- `plugins/guardrails/AGENTS.md:21` (what `~/.claude/CLAUDE.md` links to) reads: "A request someone makes (an idea,
  need, improvement or problem) in a repository with `docs/spec/` → load skill `sdd-intake` to record it as a NEED; a
  defect or gap your work finds → route it by type where found (skill `sdd-intake` § 4), a NEED only for a missing
  capability or an owner decision too large for one question or left unanswered; a request on another topic → say so
  and offer a follow-up or a new session before starting it."
- `plugins/guardrails/evals/sdd-intake-trigger-new-idea/prompt.md`: `append_system_prompt` takes that bullet
  (`check_kit.py` fails when the two differ).
- `plugins/guardrails/skills/sdd-plan/SKILL.md` § 1: a fix that § 4 or `sdd-specify` routes to a delivered FEAT or to
  code no FEAT owns needs no NEED; its finding stands in for it, the next version block (or the new FEAT) names the approved REQs the
  fix restores or, for a defect no artifact states, the finding and a criterion the failed check proves, and a
  FEAT without `## Versions` first gains the section, its delivered rows in a first block with `Status: delivered`
  and a `Scope:` line naming every REQ the FEAT lists. § 2: a defect the FEAT shipped is a fix row on it.
- Pointers to § 4 where a finding is made or routed: `sdd-constitution/references/sdd-process.md` lines 9 and 14,
  `sdd-review/SKILL.md` § 4, `sdd-release/SKILL.md` § 7 and Done when, `investigate/SKILL.md` § 5, `sdd-check/SKILL.md`
  § 4 (its row routes serve the NEED or FEAT under check; an `all` audit and drift the change did not write go by § 4
  where a type matches, else by those routes) and § 1 (a FEAT or block opened for a routed fix reads its finding for
  the NEED), `sdd-clarify/SKILL.md` § 3 (drift this NEED did not write; the NEED names the row or PR that takes it) and
  § 4 (a `decision` NEED from a finding routes its answer before `delivered`), and
  `security/references/vulnerability-process.md` (Outputs, S2, Postconditions, History).
- `sdd-review/references/closure-record.md`: a returned closure names the spec PRs and owner questions it filed too;
  `sdd-constitution/references/sdd-parameters.md` (`needs`): with `false`, only §§ 1–3 of `sdd-intake` are skipped.
- `plugins/guardrails/templates/spec-process.md` Postconditions example: "a fix row" for "a fix NEED".
- `plugins/guardrails/INDEX.md` regenerated (`gen_index.py`); `CHANGELOG.md` under `## [Unreleased]`, `### Changed`.

## Out of scope

- Requests from people: the NEED types (`new`, `improvement`, `fix`, `content`, `platform`, `decision`) and the
  `sdd-specify` routing stay as they are; a bug a user reports still enters as a NEED, which `sdd-specify` routes.
- Whether a pre-existing finding blocks `refined` or `planned`: the `sdd-check` half of the open proposal #380. This
  FEAT replaces only the line #380 proposes for `sdd-clarify` § 3 ("recorded with `sdd-intake` as a NEED of its own").
- The Stratics NEEDs already opened from findings (NEED-005, 006, 013, 016, 017, 019 to 029): re-routing or closing
  them is a Stratics change the owner decides.
- An eval case that proves a finding does not become a NEED: `.github/CONTRIBUTING.md` § Evals asks no new case for a
  skill change; a follow-up may add one.
- No release: the owner decides the version (a MINOR change by `.github/CONTRIBUTING.md` § Versioning, since routing
  changes).

## Plan

### Tests

The change is text an agent reads: no executable behavior changes, so no test fails before it (the PR's `## Red`
opens with `Exception`). CA-1, CA-8 and CA-9 are the kit's gates; CA-2 to CA-5, CA-7 and CA-10 are greps, each with
its base result; CA-6 is the trigger case that `.github/CONTRIBUTING.md` § Evals asks for when a trigger bullet or a trigger
skill's description changes.

### Risks

- An agent could call a product change a "spec fix" to skip the owner. A spec fix needs another approved artifact or a
  recorded owner decision that already states the code's behavior; silent text with a real choice is a product choice
  (one owner question); the spec PR lists each spec fix for product, and the report that found a finding names its
  route, so a review sees it.
- A product choice could be lost between sessions: one left unanswered when the session ends becomes a `decision`
  NEED (a request for `sdd-specify`, or an issue, where the project keeps no NEED file), so it is recorded.
- Opening a version block on a FEAT written before KIT-096 rewrites a delivered body into a first block. Stratics did
  it five times and the validator passes it (Problem); the kit names the step only here and in `sdd-plan` § 1.
- Only the positive trigger is measured (CA-6): no case checks that a finding stays out of `sdd-intake` §§ 1–3.

## Decisions

- 2026-11-18 (owner direction, through the Stratics coordinating session): chose routing by type at the finder over a
  lighter NEED for findings (a NEED that `sdd-intake` routes at once), because that still costs a file, a spec PR and
  a session per finding, which is what produced NEED-019 to NEED-029; and over a findings log, which would be one more
  artifact to keep.
- 2026-11-18 (#393): chose `sdd-intake` as the rule's one home over `sdd-process.md` and over a new skill, because the
  always-on bullet already loads `sdd-intake` for this decision, `sdd-process.md` is at the 60-line limit of a
  reference (`check_kit.py` `REFERENCE_MAX_LINES`), and a new skill is only for a topic no skill owns
  (`.github/CONTRIBUTING.md` § Adding content).
- 2026-11-18 (#393): counted a defect nobody would choose (a crash, lost data, a red check) as a fix even when no
  artifact states the right behavior, because `sdd-review` § 4 needs a route for "broken behavior no artifact states"
  and the owner's words put bugs outside NEEDs. The same defect reported by a person stays an `improvement` NEED
  (`sdd-specify` § 1, kept by this FEAT's brief): the PR asks the owner whether `sdd-specify` should follow.
- 2026-11-18 (#393): a product choice is too large for the finder when it needs more than one question to settle,
  since one question is what § 4 allows.
- 2026-11-18 (#393 check): chose `sdd-plan` § 1 to open a delivered FEAT's fix block with no NEED over a new fix FEAT,
  because a FEAT is one use case for the project's life and a second FEAT for the same actor and goal is `sdd-check`
  C23; code no FEAT owns gets a new FEAT the same way.
