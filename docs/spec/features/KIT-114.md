# KIT-114 — Name a plugin agent as `<plugin>:<profile>` in a skill's `agent` field

## Problem and evidence

[FACT] `sdd-check` declared `agent: researcher` and `review` declared `agent: reviewer`, but all 35 of 35 forked
`sdd-check` runs and 4 of 4 forked `review` runs of the Stratics sessions of 2026-11-17/18 ran as `agentType:
general-purpose` on `claude-opus-5-5`, not as the kit's `researcher` (`model: sonnet`, no Bash). Source: issue #388.

[FACT] Probe of 2026-11-19 (Claude Code 2.1.287, `claude -p "/probe-<n>" --model haiku` in a scratch project; three
skills with `context: fork` that differ only in `agent:`; `agentType` and model read from each session's
`subagents/agent-*.meta.json` and `.jsonl`): `agent: guardrails:researcher` ran as `agentType: guardrails:researcher`
on `claude-sonnet-5-5`, the profile's `model: sonnet`; `agent: researcher` and no `agent` both ran as
`general-purpose` on the parent's `claude-haiku-4-5`. The bare name falls back silently. Result posted on #388.

[FACT] `check_kit.py` looked `agent` up by the bare profile name in `agent_owners`, so it passed the form that does not
resolve and would have rejected the one that does.

## Scope

- `plugins/guardrails/skills/sdd-check/SKILL.md` and `plugins/guardrails/skills/review/SKILL.md`: `agent:` becomes
  `guardrails:researcher` and `guardrails:reviewer`.
- `platforms/ci/validations/check_kit.py` (section 5, the skill's `agent` check): a name with a colon must be
  `<plugin>:<profile>` where the profile is defined in that plugin's `agents/`; a bare name that matches a kit profile
  fails with the prefix to use; a bare name with no profile keeps its old failure; the reachable-plugin rule is
  unchanged.
- `platforms/ci/validations/test_check_kit_skill_use.py`: tests for the real kit and each wrong name.
- `docs/templates/kit-skill.md`: the commented `agent:` line shows the qualified form.
- `.github/CONTRIBUTING.md` (the subagent-skill line), `docs/spec/spec.md` row and `CHANGELOG.md`: one line each.

## Out of scope

- The NEED-010 replay that issue #388 names as its own test (five Stratics check inputs on the changed check): it needs
  that project's transcripts and stays open on #388.
- Devin: its CLI refused the scratch workspace as untrusted, so whether it accepts the colon form is unprobed; the
  field is a plain string in `skill.schema.json`.
- Other skills: none other declares `agent:`.

## Plan

### Tests

Written first: three of the four new tests failed on the old `check_kit.py` (the real kit still named the bare agents,
the qualified name was rejected, the wrong names gave the old message or none); the fourth case, an unknown bare name,
passed before and after. The skill frontmatter change is a one-line edit proved by CA-1 and CA-4. Evals: both skills'
descriptions and triggers are unchanged, so `.github/CONTRIBUTING.md` § Evals asks for no run; the six `trigger` cases
were run by hand anyway.

### Risks

- A fork that now runs as `researcher` has no Bash (`tools: Read, Grep, Glob`). The 1,802 Bash calls of the old runs
  were the parent's `general-purpose` tools; `sdd-check` takes its git facts as arguments (`base-diff=`, `since-diff=`),
  so it should not need them. If a run fails for lack of a tool, widen the profile, not the skill.
- The cheaper model may miss a finding the Opus run reported. #388's own test (the NEED-010 replay) measures it and is
  not done; until then the saving is unproven.
- Devin and Codex read the same `SKILL.md`. Codex loaded a skill with the qualified field and ran it (probe,
  2026-11-19); Devin is unprobed.

## Decisions

- 2026-11-19 (#388): chose to make `check_kit.py` fail the bare name, not only accept the qualified one, because the
  bare name is the silent fallback this FEAT removes; a bare name that no kit profile has keeps its old failure.
