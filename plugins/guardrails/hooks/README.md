# Guardrails hooks

[`hooks.json`](hooks.json) holds every hook of the kit as an inline `python3 -I -c` command (isolated: neither the working directory, which is the project's, nor `PYTHON*` variables nor the user site reach `sys.path`, so a `json.py` planted in the project cannot run inside a hook; `test_hooks_isolation.py`, #352), except the path-rule hook, which runs [`path_rules.py`](path_rules.py) beside it with the map [`sync-profiles.txt`](sync-profiles.txt) (KIT-081 stage 3). The format-and-lint and path-rule hooks read the project profile's `spec_root` and `stacks` through [`hook_profile.py`](hook_profile.py) (KIT-087 P2a): it runs the kit resolver `platforms/tools/profile.py resolve --json` (from `$AI_KIT_DIR`, the kit checkout the plugin runs from, else `~/.ai-kit`; `python3 -S`, 3 s timeout) and caches the view per session in `${CLAUDE_PLUGIN_DATA}/profile/<session_id>.json`, keyed by the modification time and size of the root's `.ai-kit.yaml`, its `CLAUDE.md` and the resolver; any failure gives no view, and the hook keeps its behaviour from before the profile. A failure is cached like a view: a resolver that exceeds the 3 s timeout on the session's first call (a cold disk, a loaded machine) leaves that session without a view, so with `docs/spec` and every `.gd` file linted, until `.ai-kit.yaml`, `CLAUDE.md` or the resolver changes, which is by design (one slow run per change, never one per tool call); a new session resolves again. A cached view that is not a dict with a string `spec_root` and a dict `stacks` (a corrupt cache file) resolves again instead of reaching the hook (#352). Measured on macOS with the system `python3` 3.9.6: the first call of a session adds about 75 ms (one resolver run), a cached call up to about 10 ms. Hooks are a guard, not a guardrail: they fail open, load in Claude Code, local Devin and, once the user trusts them, Codex (codex-cli 0.164.0 probe; the events Codex has, KIT-081), and cannot replace user confirmation or the always-on safety boundaries. Reader: a kit contributor who changes a hook or its tests. Paths are from the kit repository root, and the test files are in `platforms/ci/validations/`.

## Hooks

The timeout ceiling is the most `platforms/ci/validations/check_kit.py` accepts for the event; `hooks.json` may set less.

| Hook | Event, matcher, timeout ceiling | Behaviour | Tests |
|---|---|---|---|
| Guard | `PreToolUse`, `^(exec\|Bash)$`, 10 s | Denies a destructive command. Its one network call, the KIT-020 merged-branch check behind `git branch -D <name>`, fails closed: any `gh` or `git` error or timeout denies. | `hook_guard_cases.json`, run by `check_kit.py`; `test_hooks_guard_merged_branch.py` covers the merged-branch check with a stub `gh` |
| Git context | `PreToolUse`, `^(exec\|Bash)$`, 10 s | Only adds context and never denies (KIT-071): after a `git commit` or `gh pr create` it adds the `git` essentials for the next step. Claude Code shows `additionalContext` next to the tool result, so it reaches the model after the command ran. `check_kit.py` tells it by its `ai-kit git, after this ` text. | `hook_git_context_cases.json` (commit, PR and silent commands), run by `check_kit.py`; `test_hooks_context.py` |
| Format and lint | `PostToolUse`, `^(edit\|write\|Edit\|Write)$`, 30 s | `gdformat` and `gdlint` on a `.gd` file in a folder whose profile `stacks` include `godot` (every `.gd` file when the profile sets no stacks), `check_spec.py` on the spec when a Markdown file under `spec_root` (default `docs/spec`) changes, both from the git top level (KIT-087 P2a). A missing tool exits 0 with a notice; findings exit 2 with the tool output on stderr; the profile never blocks. | `hook_post_edit_cases.json` covers every branch; `check_kit.py` runs it with stub tools; `test_hooks_profile.py` covers `spec_root`, `stacks`, the cache and the fallback |

| Path rules | `PostToolUse`, `^(Read\|Edit\|Write\|MultiEdit\|NotebookEdit\|Bash\|Grep)$`, 30 s (`hooks.json` sets 5 s); `SessionStart`, `^compact$`, 5 s | Only adds context and never blocks (KIT-081 stage 3): in a project whose `CLAUDE.md` starts with the `sync-project.sh` marker, it gives each kit rule the project's stacks select through `sync-profiles.txt` (the profile's `stacks` through `hook_profile.py`, KIT-087 P2a, else the marker's profiles) when the call names a file the rule's `paths` match (`file_path`, `notebook_path`, `path`, a path-like word of a Bash command, or, for Codex's `apply_patch` call, whose `tool_input.command` is the patch text and which has none of those keys, the path of each `*** Add File:`, `*** Update File:`, `*** Delete File:` and `*** Move to:` header at the start of a line, a `+`, `-`, space or `@@` body line never counting, the first 64 paths of the first 1 MiB; relative to `$CLAUDE_PROJECT_DIR`, else the event's `cwd`), once per session (`${CLAUDE_PLUGIN_DATA}/path-rules/<session_id>.json` under a lock, pruned after 3 days; a rule is recorded only after its text is read; on `SessionStart` with source `compact` the script deletes the session's file, so a compaction that dropped the rule text gets it back, #325), as `additionalContext` that names the rule, its globs, the file and where the kit files it names are, then the rule body. Each delivery appends a `kit_hook_path_match` record to the rule-load log. In Codex the matcher needs no `apply_patch` entry: its hooks doc matches `apply_patch` through the `Edit` and `Write` aliases, and the probe of #308 (codex-cli 0.164.0) saw the plugin hook fire before and after one; a Codex user must trust the plugin's hooks, as Codex skips an untrusted one silently (KIT-081 stage 3 for Codex). Anywhere else, without `CLAUDE_PLUGIN_DATA`, or on any error it prints nothing and exits 0. `check_kit.py` tells it by its `/hooks/path_rules.py` command. | `check_kit.py` runs it on eight cases in one throwaway synced project (a Read, the repeat, a Bash read, another profile, a compaction through the `SessionStart` command, the Read after it, no marker, malformed input) and checks the log; `test_hooks_path_rules.py` covers the globs, the Bash words, the `apply_patch` headers, the gate, the profiles, the state, compaction, the claim order, the log, parallel calls, failures and the latency budget |
| Rule-load log | `InstructionsLoaded`, no matcher, 5 s | Only records (KIT-070): for each `CLAUDE.md` or `.claude/rules/*.md` load it appends one JSON line (time, session, cwd, file path, memory type, load reason, globs, trigger and parent file; never content or the transcript path) to `${CLAUDE_PLUGIN_DATA}/instructions-loaded.jsonl`, rotated past 5 MiB under one lock with the append (`instructions-loaded.jsonl.lock`, `flock` where the platform has it, so concurrent sessions lose no line, #274), prints nothing and exits 0. `platforms/tools/skill_usage.py --rules` counts it. `check_kit.py` tells it by its `ai-kit rule-load log` text. | `check_kit.py` runs it on one path-rule load with a throwaway data folder; `test_hooks_instructions_loaded.py` covers malformed input, a missing or unwritable data folder, the rotation, latency and broken copies that `check_kit.py` must fail |

- Attribution line: both start hooks add the commit trailer and PR footer, which `includeGitInstructions: false` removes from Claude Code's prompt, only while the user, project and local settings files leave that key at `false`, with the user's own `attribution.commit` and `attribution.pr` text where set and nothing for an empty one, `attribution: false` or `includeCoAuthoredBy: false`.
- Settings cases: `check_kit.py` runs both start hooks on four settings cases (off, default, hidden attribution, a custom trailer) with an empty `HOME`; `test_hooks_context.py` covers the settings layers, malformed input, latency and broken copies that `check_kit.py` must fail.
